# Решатель задач MedAssist: проект и план развития (5 семестр)

Документ фиксирует архитектуру решателя, принятые проектные решения, соглашения разработки
и план задач второго этапа. Раздел «Состояние задач» обновляется вместе с кодом.

## 1. Назначение и разделение работ

Решатель получает описание взрослого пациента и решает задачи над базой знаний MedAssist:

| Часть | Ответственный | Классы задач |
|---|---|---|
| Диагностика и оценка срочности | Соловьёв Н. Л. | триаж, диагностика, объяснение; разбор текста врача |
| Маршрутизация и выбор тактики | Миронов Т. Э. | выбор маршрута и протокола, подбор терапии с ограничениями, объяснение; справочный режим |

Обе части работают над общим ядром (разбор задачи, прямой вывод, шкалы, вопросы, объяснения)
и общей точкой входа `solve()`.

## 2. Конвейер решения

```text
запрос ──► facts.parse_case ──► engine.run ──────────────► модули этапа 2 ──► api: ответ
           коды, диапазоны,     профили, шкалы,             routing (T1)        состав по роли,
           ограничения схемы,   красные флаги,              protocols (T2)      вопросы,
           выводимые факты      неотложные состояния,       therapy (T3)        дисклеймеры
                                правила до неподвижной      ranking (D1–D3)
                                точки, трасса
```

Модули этапа 2 работают **после** неподвижной точки вывода: им нужны итоговые рабочие диагнозы,
шкалы и распознанные состояния. Каждый модуль:

- читает знания только из базы (поля машиночитаемого слоя, правила, словарь схемы);
- оценивает условия в трёхзначной логике и не трактует «неизвестно» как «нет»;
- дописывает шаги в общую трассу вывода (`memory.trace`) — каждый вывод объясним;
- возвращает результат простыми типами (словарь сериализуется в JSON без преобразований);
- может повысить срочность, но никогда не понижает её.

## 3. Принятые решения (общие для всех модулей)

1. **Знания вне кода.** Медицинские пороги, идентификаторы карточек и соответствия хранятся в базе
   знаний или в схеме (`input_constraints`, `solver`, словарь фактов). Код содержит только алгоритм.
2. **Открытый мир.** Несообщённое значение — «неизвестно». Вывод, зависящий от неизвестного, не делается;
   вместо него формируется вопрос с полем ввода (`questions[].inputs`), ответ подставляется `apply_answers`.
3. **Безопасность прежде полноты.** Если более тяжёлый вариант (маршрут, состояние) нельзя исключить
   из-за нехватки данных, он не отбрасывается молча: вывод помечается как предварительный и задаётся вопрос.
4. **Монотонность.** Новые сведения о проявлениях только добавляют выводы: срочность не понижается,
   распознанные состояния не исчезают, веса гипотез не уменьшаются (проверяется инвариантами).
5. **Детерминированность.** Порядок обхода карточек и правил фиксирован; одинаковый вход — одинаковый ответ.

## 4. Соглашения разработки

- Новый модуль — файл в `src/solver/`, функция над `Conclusions` и `KnowledgeBase`, вызов из `api.solve`.
- Новое поле базы знаний — сначала в схеме (`kb/_schema/schema.yaml`), затем в карточках; валидатор
  проверяет его автоматически по описанию в схеме; `python scripts/rebuild_all.py` пересобирает документацию.
- Обязательные проверки перед коммитом: `python -m pytest -q`, `python scripts/rebuild_all.py`
  (0 ошибок валидации), `python scripts/run_solver_cases.py` (отчёт о сценариях).
- Каждое новое правило или поле машиночитаемого слоя покрывается сценарием в `tests/cases/`.
  Ожидаемый результат записывается **до запуска** по клинической логике и сопровождается комментарием
  с расчётом; при расхождении исправляется база знаний или код, а не ожидание.
- Автоматические проверки, которые распространяются на новые знания сами:
  достижимость каждого правила и карточки (`test_reachability.py`), полнота вариантов шкал,
  устойчивость к некорректному входу (`test_robustness.py`), инварианты (`test_invariants.py`).

## 6. T1. Маршрутизация (проект)

**Активация карточек.** Карточка `routing` рассматривается, если её поле `for` пересекается с рабочими
диагнозами, распознанными неотложными состояниями или сообщёнными симптомами, либо на неё передал
управление красный флаг или неотложное состояние (поле `action`).

**Выбор строки таблицы решений** (строки упорядочены от тяжёлого маршрута к лёгкому, что проверяет валидатор):

```text
нерешённые := []
для каждой строки по порядку:
    если условие истинно:      выбрать строку, закончить
    если условие неизвестно:   нерешённые += строка
если ни одна строка не выбрана: выбрать маршрут по умолчанию
предварительно := есть нерешённая строка с маршрутом тяжелее выбранного
если предварительно: вопрос «чтобы исключить <маршрут>, уточните …» с полями ввода
```

**Итоговый маршрут** — самый тяжёлый из маршрутов карточек и правил (`route`). Тяжесть и соответствие
маршрута срочности задаются в схеме (`solver.route_severity`, `solver.route_urgency`): экстренный маршрут
повышает срочность до экстренной. Срочность других маршрутов не выводится из их вида: срок направления
различается по нозологиям (24–72 часа при АГ, 2–4 недели при ИБС) и задаётся полем `timeframe`.
Экстренная срочность без маршрута означает экстренный маршрут (`solver.urgency_route`).

**Следующие шаги** строки (`next`) — протоколы и алгоритмы неотложной помощи — добавляются в список
дальнейших действий; планы наблюдения передаются модулю T2.
